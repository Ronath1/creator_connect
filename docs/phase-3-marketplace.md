## Database boundary

The normal application uses the current Clerk JWT and Supabase publishable key. A dedicated `marketplace_executor` PostgreSQL role is NOLOGIN, NOINHERIT and has no BYPASSRLS. It is never granted to application roles. Its narrowly granted table permissions and explicit RLS policies support transactional functions in the non-exposed `marketplace_private` schema. These functions use an empty search path, derive identity from the verified JWT, and check current membership, profile completeness, role, ownership and lifecycle conditions. Public RPC entrypoints are security invoker wrappers. No caller-set bypass flag or privileged application key is used.

This trusted database boundary allows selection to update the application and collaboration together, and gives Phase 4 a safe path for a creator's agreement confirmation to update the brand's slot and competing applications atomically. Direct lifecycle DML is unavailable to ordinary callers. Member-facing projections omit identity-provider identifiers, emails and membership records.

## Scope and invariants

- Own profile editing continues through existing validated onboarding services. Active, complete members can view safe member profiles and published opportunities; draft and applicant data remain private.
- Opportunities contain exact positive LKR amounts, server-validated deadlines, platforms, category, revision allowance and one to ten deliverables. Draft, publish, non-material edit, close and reopen follow the accepted Phase 0 rules. Published history is retained. Material fields freeze once an application exists, enforced in the database.
- Lists default to 20 and cap at 50. Discovery supports bounded title/brief search, category and platform filters. Forms and result cards support phone widths, persistent labels, 16 px fields and 44 px controls.
- One application exists forever per creator/opportunity. Withdrawn applications cannot be resubmitted. Only the applicant and owning brand see the application.
- Every competing mutation locks the opportunity first. Selection reserves one slot and creates the pending agreement snapshot in one transaction. A uniqueness constraint backs the slot invariant. Pending agreement is visibly distinct from mutual agreement.
- Server reconciliation closes expired opportunities, expires pending reservations and applies the accepted seven-day selection windows. A live reservation preserves competing pending applicants. Release starts a fresh window bounded by delivery; reopening before the application deadline resumes ordinary open rules.
- Persisted history/events preserve corrections and application/selection decisions for the Phase 4 notification consumer. Notifications and mutual agreement actions are delivered in Phase 4.
