This extends the [anonymous HTTP baseline](phase-8-performance.md) without touching the application, DEV data or deployment. No Redis, index/RLS/schema change, paid service or Phase 9 implementation is introduced.

## Run locally

Use the repository's existing Node >=22.13 environment and pinned PGlite dependency. No server, Docker, Clerk account, Supabase target, network connection, credential or `.env` is needed.

```sh
npm run perf:sql -- --help
npm run perf:sql
npm run perf:sql -- --samples 1
npm run perf:sql -- --samples 20
```

`--samples` is an integer from 1–20, default 5, **per operation**. Help and invalid arguments return before importing/starting PGlite. Exit 0 means all assertions passed; exit 1 means a diagnostic/setup/integrity failure; exit 2 means invalid arguments. Failure output contains only phase, a static failed-check label where applicable and SQLSTATE/generic code; raw SQL exceptions, IDs, bodies and payloads are never logged. There is no fixed speed threshold.

The script creates one **in-memory, single-connection** database and closes it in `finally`; nothing is persisted or connected to existing services. It reads 11 immutable migration files, from identity/onboarding through portfolios, and reports their count plus a combined SHA256 over each ordered filename, newline, exact SQL text, newline. It excludes `20261113125515_phase_4_durable_jobs.sql` because real `pg_cron` is unavailable; conditional scheduler changes in later migrations do not run. It never invents a cron implementation. Minimal empty Storage catalogs satisfy migration DDL; no object operations/scanner run and no hosted gateway is present.

## Canonical fixture and trust boundaries

Every run starts with exactly **50 completed profiles (10 brands/40 creators), 100 opportunities, 500 applications, 50 active mutually confirmed collaborations and 2,000 messages**. Each opportunity has five distinct applicants; the first 50 select one applicant and receive both confirmations. Each collaboration receives 40 participant messages. All terms/deadlines are valid and relative to that run, avoiding accidental expiry during this short diagnostic.

Topology, text and supplied membership/opportunity/message request UUIDs are deterministic; normal application/collaboration/item UUIDs generated by the database remain opaque and are not rewritten. This is a reproducible fixture shape, not a byte-identical database dump. There are no real people, uploads or publications.

Explicit privileged fixture operations, all untimed as application samples:

- Create local roles, synthetic `auth.jwt()`/claim plumbing and minimal Storage catalogs; apply unchanged repository migrations under the local fixture administrator. These are test support, never application authentication code or proof of real JWT verification.
- Insert only the 50 synthetic membership rows as fixture administrator. All profile onboarding, opportunity create/publish, applications, selection, mutual confirmation and message seeding then use the **actual public RPCs** under authenticated test-role/subject contexts. No direct domain-row inserts replace those RPCs.
- Temporarily suspend one exact synthetic creator and restore it in `finally` to verify the real membership checks. This direct fixture toggle is not measured administrator behavior or a support-UI test.
- Read aggregate counts/relationships as fixture administrator for verification. Such privileged reads are integrity evidence only, never authorization success.

Synthetic claims are not real Clerk sessions. The script does not weaken app authentication, pass privileged claims to a server or load any app service/credential module.

## Measured operations and assertions

Each sample performs four bounded public-RPC reads: discovery, published opportunity detail, own applications and participant collaboration detail. Three **committed** writes follow: a new application by a previously nonapplying creator to a distinct open opportunity, withdrawal of that exact application, and a new participant message. No preserved DEV fixture is used. Setup, onboarding/seed, denial guards and final administrator verification are separately timed and excluded from operation durations.

For N samples, final counts must be **50 / 100 / (500+N) / 50 / (2000+N)**. The N extra applications must all be withdrawn; messages and all successful business calls are committed, not rolled back for nicer results. Every collaboration must retain its effective version with both confirmations, valid selected-application relationship and participant message authors. No file/public portfolio is created. The original 50 memberships must be restored active within the disposable database before closure.

Twenty-three named checks cover exact initial/final counts, actual 50-row discovery cap and disjoint pages, bounded applicant/message pages, own/competing application isolation, outsider hidden detail and post-run agreement/relationship/no-file integrity. Seven separately counted expected denials cover anonymous, uninvited, outsider message, foreign brand status change, raw lifecycle DML and suspended read/write. They are not counted as unexpected performance errors. Any failed assertion or unexpected RPC error stops the run with exit 1; application/schema fixes need parent review of a demonstrated defect.

Each operation reports committed call count, unexpected errors and nearest-rank elapsed min/p50/p95/max. **Exact timing boundary:** JavaScript wall time around the PGlite transaction including `SET LOCAL ROLE`, synthetic claim setup, public RPC, result materialization and commit. It includes JS/WASM and transaction overhead; it is not SQL-engine-only or application-server p95. Guard/assertion work between measured calls appears only in the measured-phase wall interval. Seed/setup timings remain separate and no raw query/result is output.
