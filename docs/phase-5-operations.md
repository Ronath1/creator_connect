Startup order to validate on the selected host: database/schema/issuer and secrets → private ClamAV with fresh signatures/UTC/alerts → narrow attachment worker configuration → application ingress → deliberate activation of owned SQL jobs and supervised cleanup. There is no implemented general maintenance/read-only toggle: suspending members alone does not stop already authorized privileged uploads. An incident requiring a write freeze must stop/drain app and worker ingress/processes through the chosen host's tested controls.

## Incident procedure

Proposed severity: critical = suspected cross-user access, secret exposure, lost/corrupt accepted terms or linked evidence; high = core workflow outage/scanner or job failure; normal = bounded friction with safe workaround. No response-time guarantee exists until staffed support is accepted.

1. Record incident ID/time/timezone, reporter, affected environment/commit and a minimal redacted symptom. Assign owner/operator; preserve relevant immutable event/audit IDs, metadata/hash evidence and restricted logs. Do not reproduce attacks on real users or copy private files into chat.
2. Contain using tested host controls: stop affected ingress/uploads/workers for suspected write/privacy corruption; stop owned jobs if they would compound damage. For a compromised identity, suspend its membership and separately revoke Clerk sessions; for a secret exposure, restrict the affected service and rotate/revoke the actual secret through its owner. Removing a value from Git is not revocation. Do not publish broadly privileged temporary keys or disable RLS/scanning to recover availability.
3. Determine blast radius: target/issuer/key/environment mismatch, actual ACLs/RLS, current membership, direct Storage visibility, object metadata/hash vs immutable record, event/cron backlog and recent deployment. For native JWT failures, verify fresh token trust/configuration privately; never substitute the worker key for ordinary user access. Business conflicts use `PT409`, never `40001` retry loops.
4. Recovery requires a reviewed fix or compatible prior application artifact. Rollback code only after checking schema compatibility; never roll back by rewriting applied migrations or deleting evidence. Reconcile incomplete writes using request IDs/current state, not blind repeated submissions. If restore is needed, use the isolated drill below and explicit owner approval before cutover.
5. Verify the affected path plus access-denial cases before restoring ingress/jobs. For file issues check actual storage absence/hash and user/case authorization, not cached download bytes. Inspect outbox/cleanup retries for duplicates/backlog. Communicate scope, workaround and next update through the nominated contact; do not promise funds/refunds in this non-transactional pilot.
6. Close only after owner review: timeline ___; impact/affected scope ___; containment ___; cause/evidence ___; fix/verification ___; data reconciliation ___; notification decision ___; follow-ups/owners ___; reopen criteria ___ . Keep incident evidence under the accepted privacy/retention process.

## Backup inventory and isolated restore rehearsal

Owner must choose and document **RPO** (maximum acceptable data loss) ___ and **RTO** (acceptable recovery duration) ___, backup cadence/location/encryption/access/retention ___ and restore operator ___ . These fields are unset proposals; no recovery guarantee or backup entitlement is assumed. Verify chosen plan/features and price at selection time.

Supabase database backups do **not** include Storage object bytes. Back up/restore bytes separately for `profile-images`, `collaboration-quarantine` and `collaboration-files`, with object keys, counts, sizes and integrity manifest in protected storage. Do not assume a new-project restore copies buckets/settings or external configuration. See official [database backup scope](https://supabase.com/docs/guides/platform/backups) and [restore-to-new-project limitations](https://supabase.com/docs/guides/platform/clone-project), checked 16 November. Follow the then-current supported restore method/CLI help; this runbook deliberately provides no destructive production restore command.

Inventory beyond database rows: full migration ledger, role/function ownership and ACLs, RLS/policies/triggers/constraints/indexes, pg_cron schedules, app artifact/lockfile, bucket privacy/limits/policies, scanner configuration/signature policy, external Clerk identity/issuer mapping, environment names and secret-rotation custody. A DB restore does not restore Clerk accounts or prove fresh JWT trust. Do not store raw secrets inside backup manifests or assume restored role passwords/keys remain valid.

Rehearsal steps (not executed):

1. Obtain owner-approved isolated target and protected backup access; record exact source/target identifiers and selected recovery point. Deny public traffic. **Before importing or starting restored automation**, ensure target jobs are inactive, no cleanup worker/application is running and outbound access cannot mutate source projects/buckets. Some restore methods may start copied jobs: choose a supported method that permits isolation/disabled execution first; do not rely on racing a post-restore disable. No restored process may hold source Storage credentials.
2. Establish a consistent capture boundary using the chosen host's verified write-freeze procedure: stop/drain writes and in-flight uploads (whole upload bound 120s, then confirm no active operations), pause cleanup/owned mutations and record database/object snapshot times. Preserve immutable linked objects and pending reservations; do not discard uncertain bytes just to simplify a snapshot. Record the allowed consistency window and any unavoidable lag for RPO assessment.
3. Restore into the isolated target using reviewed provider tooling. Preserve internal UUIDs, agreement versions/confirmations, submission/item/revision identities, cancellations, audit/history, reports/assignment and attachment hashes/links. Do not re-import bootstrap fixtures, remap roles or regenerate IDs. Keep restored cron and workers **disabled** until bytes/metadata are reconciled.
4. Restore private object bytes and settings to target buckets only; compare counts/bytes/keys to manifest and every linked attachment’s size/hash, including main evidence paths and prior versions. Check profile bytes separately; confirm orphan/quarantine accounting and cleanup claims are consistent. Missing/mismatched evidence blocks cutover, even if pages render. Never point a restored DB at source buckets as a workaround.
5. Verify exact actual ACLs/RLS and dedicated executor NOLOGIN/NOINHERIT/NOBYPASSRLS, no ordinary role membership/CREATE or postgres SET grant, non-exposed private schema, public invoker wrappers and worker-only finalization. Run direct anonymous, outsider, suspended and assigned-case denial checks with isolated synthetic identities. Check no source/test identities accidentally gain target membership.
6. Re-establish deliberate Clerk environment mapping without touching real accounts. Preserve production subject mapping for an actual recovery; for a drill use controlled target identities/mapping and document what this cannot prove. Fresh real JWT tests must prove issuer, own membership and cross-user denial. Secrets are reconfigured privately, not read from backup logs.
7. Start isolated app/scanner with target-only keys. Validate agreement history, full submission/review evidence, authorized hash-verified download and denied raw Storage/cross-user access. Deliberately re-enable target jobs/cleanup only after reconciliation; verify deduped outbox/retry and that cleanup never removes linked evidence. Observe job successes, not just schedules. Re-disable/dispose only approved drill resources after recording results.
8. Record backup timestamp/consistency window ___; restored point ___; recovery started/usable/end times ___; actual lost interval vs RPO ___; actual recovery duration vs RTO ___; row/object/hash/ACL/JWT results ___; defects ___; operator/owner review ___; cutover/rollback decision ___ . A rehearsal does not authorize production replacement. Owner approves any real cutover and source retention/decommission separately.

## Pilot-end retention review

Record owner-declared pilot end ___ and 90-day review date ___ . Shared evidence/audit is retained through that review; owner must approve deletion/export or extension with access restrictions and confirmation of related participants’ rights/process. Reconcile object bytes, DB records and protected backups under the approved policy; no broad cascade deletion or indefinite default extension. Uncertain pending bytes follow **24-hour grace plus scheduling/retries**, not a 24-hour deletion guarantee. Account deletion and Clerk session revocation are separate from shared-evidence retention. These procedures need owner acceptance before invitations, not after the first request.
